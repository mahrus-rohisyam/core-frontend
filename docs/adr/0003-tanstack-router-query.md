# 0003. Use TanStack Router and Query with a generated API client

- Status: Accepted
- Date: 2026-11-08

## Context

Hand-written fetch calls and response types drift from the API over time. Filters and pagination kept in
component state are lost on reload and cannot be shared as links.

## Decision

- Routing: TanStack Router with typed params and search params. `core-shell` builds the router
  (`createCoreApp`) with the sign-in, account and settings routes; the app adds its own routes under
  the organization route. Guards redirect in `beforeLoad`, not by rendering a redirect component.
- Server state: TanStack Query. Each module exports query and mutation factories
  (`notesQuery(org)`, `createNote()`), not ad-hoc `useQuery` calls in components.
- API calls: `core-api` wraps openapi-fetch with types generated by openapi-typescript from the backend's
  OpenAPI description (see backend ADR 0005). Hand-written `fetch` to `/api` is not allowed.

## Consequences

- A backend spec change shows up as a TypeScript error in the frontend.
- Search params in the URL hold filters and pagination, so views are shareable and survive reloads.
- Contributors who know react-router need to learn TanStack Router's file and route API.

## Alternatives considered

- **react-router.** More widely known, weaker typing of params and search.
- **SWR or plain `fetch` with `useEffect`.** Fewer concepts, but caching, retries and invalidation end up
  written by hand in each app.
- **tRPC.** End-to-end types, but TypeScript-only on the server side.
